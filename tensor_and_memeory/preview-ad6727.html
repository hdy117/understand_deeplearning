1. Tensor 先别急着当成“高深数学对象”

在神经网络的工程语境里，tensor 首先就是一块带 shape 的多维数字容器。不过要读懂它，得先把三件事分开：

维度 例子 它回答的问题
shape (2, 3, 4) 每条轴有多少个位置？
dtype float32、int64 每个数字用什么数值类型存？
device cpu、cuda 这块数据放在哪里计算？

数学里的 tensor 当然有更抽象的定义，但这里只取深度学习中最有用的那个工程含义。torch.Tensor 也并不要求“三维以上才算 tensor”——在 PyTorch 里，下面每个对象都是 tensor：

shape 里有几个数字，就说它是 rank 几（也常称有几维）：

数学名 PyTorch shape 直觉
scalar [] 一个数
vector [D] 一列或一行特征
matrix [M, N] M 行、N 列的表
rank-3 tensor [B, M, N] B 张矩阵
rank-4 tensor [B, C, H, W] 一批图像

所以记住这个关系就够了：matrix 只是 tensor 的一个特例。所有 matrix 都是 rank-2 tensor，但一个 [B, C, H, W] 的图像 batch 不会因为名字叫 tensor，就自动变成“一个巨大的矩阵”。它有四条轴，每条轴的语义都不同；一旦把这些轴弄混，代码有时仍能运行，却会悄悄算错东西——这比直接报错更危险。

2. 为什么网络总在重复“加权求和”

先从最小的神经元开始。一个 neuron 接收输入 𝐱=(x1,…,xD)，为每个输入学一个 weight 𝐰=(w1,…,wD)，再加一个 bias b：

z=w1x1+w2x2+⋯+wDxD+b.

这一步的意思很朴素：每个特征先按重要程度缩放，再把证据合在一起，最后整体平移。接下来要做的，就是给它接上 activation（对应配套笔记的第 3 章）：

h=a(z),

比如 a 取 ReLU。再把许多这样的 neuron 叠起来，就得到了一层网络（对应配套笔记的第 4 章）。而难点也在这里浮出水面：一个 neuron 手写一行加法就够了，可网络里有成百上千个 neuron，还要同时处理一整个 batch——逐个写加法既慢又容易漏连接。我们需要一个能把“很多个加权求和”打包表达出来的对象。

这就是逼出矩阵乘法的现实压力：不是为了让公式看起来高级，而是为了把大量相同类型的点积，压缩成一次规则的计算。

3. 从点积重新推导矩阵乘法

3.1 一个点积：一个 neuron 的全部输入

先从最基础的运算说起：两个长度相同的 vector 做 dot product（点积）：

𝐱⋅𝐰=∑k=1Dxkwk.

举个具体的例子：

[1,2,3]⋅[10,20,30]=1×10+2×20+3×30=140.

点积会把两个长度为 D 的向量压成一个 scalar。换个角度看，它其实就是“先逐元素相乘，再沿 feature 轴求和”：

一个 neuron 对应一个点积。那如果现在有 2 个 neuron、各自拿着一套 weight 呢？

z1=1×10+2×20+3×30,z2=1×40+2×50+3×60.

把两套 weight 叠成矩阵：

W=[102030405060]∈ℝ2×3.

把输入仍写成列向量 𝐱∈ℝ3，两个 neuron 的结果就能一次写成：

W𝐱=[102030405060][123]=[140320].

矩阵的每一行是一套 neuron weights；矩阵乘向量的每一个输出元素，都是对应行与输入向量的点积。到这里，矩阵乘法已经被我们重新推导出来了：它不是什么新东西，只是“同时做很多个点积”。

3.2 两个矩阵：很多输入、很多 neuron

如果一次处理 B 个样本，把每个样本放成一行：

X∈ℝB×Din.

权重矩阵仍然记作

W∈ℝDout×Din,

它的每一行对应一个 output neuron。不过现在样本是按行摆放的，要让 X 的每一行都和每个 neuron 做 dot product，就需要把 W 转置一下，使用 W⊤：

XW⊤∈ℝB×Dout.

做一次维度检查，原因就一目了然：

把这个例子再推进一步，就得到了矩阵乘法的通用规则：

A∈ℝM×K,B∈ℝK×N⟹AB∈ℝM×N.

中间的 K 必须相等，因为每个输出格子都要沿同一条长度为 K 的轴做求和：

(AB)ij=∑k=1KAikBkj.

i 选择左矩阵的一行，j 选择右矩阵的一列，k 则是两者对齐后被消掉的那条 feature 轴。所以“矩阵乘法要求内维相等”这句规矩，翻译过来其实很朴素：做 dot product 的两条向量必须一样长。

3.3 一个完整的小例子

接下来先把一个容易混淆的约定钉死：本节有 2 个 output neurons，每个 neuron 接收 3 个 input features。我们把每个 output neuron's weights 写成 W 的一行，因此

W∈ℝDout×Din

所以在本例中，W 就是 2×3。如果像数学教材那样把单个样本写成列向量，计算就是

W⏟2×3𝐱⏟3×1⟶𝐲⏟2×1𝐲=W𝐱.

当然，你也可以选择另一套完全等价的约定：把样本写成行向量，把 weight 存成 3×2 的转置矩阵。这时计算要写成

𝐲row=𝐱rowWrow,𝐱row∈ℝ1×3,Wrow∈ℝ3×2.

这两套写法没有对错之分，只是向量的摆放方向不同：

这里有 B=2 个样本、Din=3 个输入特征、Dout=2 个 output features。代入矩阵乘法，就是

4. Tensor 与矩阵乘法是什么关系？

走到这里，tensor 和矩阵乘法的关系就可以说得很准确了：

  1. Tensor 是容器和结构的总称，可以是 scalar、vector、matrix 或更高阶数组。
  2. Matrix 是 rank-2 tensor，有两个轴，通常解释为 rows 与 columns。
  3. 矩阵乘法是一种运算，它要求两个对象的矩阵轴对齐，并沿中间轴做点积求和。
  4. 高阶 tensor 可以携带一批矩阵。这时 torch.matmul 通常把最后两个轴当成矩阵轴，把前面的轴当成 batch 轴。

4.2 并不是所有“维度”都可以随便收缩

上一节我们已经看到，矩阵乘法的形状规则非常严格：左边最后一个矩阵轴，必须和右边倒数第二个矩阵轴一样长。但“长度一样”只是语法条件，不是语义保证。真正写模型时，还必须回答一个问题：这个被求和的 index 到底代表什么？是 input feature、局部像素，还是图上的邻居？如果只是看到两条轴都长 32 就随手收缩，代码也许能跑，模型却可能已经把完全不同的东西搅在了一起。

先把四条检查规则记下来：

  1. 先给每个轴命名。 不要只看 0、1、2、3；写出 B、C、H、W、N、D 这些语义。
  2. 写一个输出元素的公式。 公式中的求和 index，就是被 contraction 的轴。
  3. 区分“选择位置”和“求和”。 H、W 有时只是指定当前窗口的位置，并没有被全局求和。
  4. 区分 batch 处理和矩阵乘法。 batch 轴通常只是“对很多份相同结构的数据并行做同一件事”，不会和另一个 batch 轴做 dot product。

下面就用 CNN 和 GNN 各走一遍这套检查流程。它们看起来都在处理 rank 3 或 rank 4 的 tensor，但被收缩的轴截然不同。

4.2.1 CNN：收缩的是一个局部 patch，不是整张图

一批图像通常写成

X∈ℝB×Cin×H×W.

四条轴各司其职：

轴 含义 在一次卷积输出中做什么
B 同时处理的图片数 保留；第 b 张图不会和第 b′ 张图相乘
Cin 输入通道，例如 RGB 的 3 个通道 对当前局部窗口求和
H,W 空间位置 决定当前窗口从哪里开始；不会把整条高度或宽度一次性求和
Cout kernel 的数量，也就是输出通道 保留；每个 kernel 产生一张 feature map

而一个 Conv2d kernel 的 shape 是

K∈ℝCout×Cin×Kh×Kw.

为了看清到底收缩了什么，我们把一个输出元素完整写出来：

Yb,o,i,j=bo+∑c=1Cin∑u=1Kh∑v=1KwKo,c,u,vXb,c,i+u,j+v.

仔细看，这个公式其实比“卷积就是矩阵乘法”的说法更准确：

  • 被求和的是 c,u,v，即输入通道和局部窗口里的两个偏移；
  • b 被保留，所以每张图片独立处理；
  • o 被保留，所以每个 output channel 有自己的 kernel；
  • i,j 被保留，所以每个空间位置都会得到一个输出；
  • H,W 没有被整个压扁，它们只通过不同的窗口位置参与计算。

换句话说，一个输出位置仍然是一次普普通通的 dot product——不信的话，把当前窗口摊平看看：

Xb,:,i:i+Kh,j:j+Kw⏟长度 CinKhKw⋅Ko,:,:,:⏟长度 CinKhKw.

唯一的区别在于：这个 dot product 的输入不是固定的一行，而是随着 (i,j) 在图像上滑动的窗口；同一个 kernel 还会在所有位置上复用。这就是 locality 和 weight sharing。

先看核心原理：用 q @ K.T 一次说透

einsum 的全部原理其实只有一句话：给每条轴起一个名字；同名的轴先对齐再相乘；箭头右侧没被点名的轴，沿它求和后消失。对比来看，矩阵乘法是“位置驱动”的约定——永远只看最后两条轴；而 einsum 是“名字驱动”的声明——每条轴扮演什么角色，直接写在 equation 里。

拿 attention 的第一步，把两种写法并排看看：

matmul 版本要在脑子里做三件事：先想起“最后两条轴才是矩阵轴”这条约定，再把 k 的最后两轴转置成 [Dh, N]，最后检查内维 Dh 是否对齐。这一整套推理都发生在你脑子里，代码里完全看不出 Dh 被收缩。而 einsum 版本把同一件事，写成了五个字母各自的命运：

字母 绑定的轴 出现在 命运 语义
b 第 0 轴 两个输入 + 输出 对齐并保留 batch 并行，不混算
h 第 1 轴 两个输入 + 输出 对齐并保留 head 并行，不混算

j k 的第 2 轴 只在 k 和输出 保留 key position
d 第 3 轴 两个输入，不在输出 对齐、相乘、求和 feature 轴被收缩

逐元素写出来，就是那张熟悉的 score 表：

scoresb,h,i,j=∑d=1Dhqb,h,i,dkb,h,j,d.

所以以后读任何 equation，都用同样三条规则：

  1. 起名：一个字母绑定一条轴，字母数量必须等于 operand 的 rank。
  2. 对齐：同名轴逐格配对相乘，size 必须兼容——相同，或一边为 1 可 broadcast。
  3. 消元：箭头右侧出现的字母按顺序留在输出；没出现的字母沿它求和后消失。

这套写法是有渊源的——Einstein summation convention：1916 年广义相对论里，“同一项中重复出现的指标默认求和”。einsum 把它放宽成一种显式声明：只有在左右两边都出现、但右侧消失的指标才求和，输出轴的顺序也由你亲自点名。

先直接回答：不是。在 PyTorch 里，rank（也可以写成 tensor.ndim）表示 tensor 有几条轴；dim 则表示“选择哪一条轴”的编号。一个是数量，一个是位置，别再把它们混用了。

10. 常见误解：能运行不等于语义正确

10.1 “tensor 就是矩阵”

这个说法不准确。matrix 是二维 tensor，而图像 batch、视频、attention states 通常都是更高阶的 tensor。当然，你可以在特定情况下把它们 reshape 成矩阵，但 reshape 只改变索引视图，并不会自动告诉模型哪一轴是 batch、哪一轴是 channel。

10.2 “只要元素总数一样，reshape 就随便做”

reshape 只关心元素总数对不对得上，至于模型语义允不允许，它一概不管。比如把 [B, C, H, W] reshape 成 [B, C*H*W]，是把每张图 flatten，常用于接 fully connected head；但如果 reshape 成 [B*C, H*W]，就等于把 channel 当成了独立样本——这通常已经悄悄换了问题。

10.3 “transpose 和 reshape 都是在换形状，所以可以互换”

不可以，两者分工不同。transpose / permute 交换的是轴的解释，reshape 重新组织的是元素的线性视图。还以 attention 为例：k.transpose(-2, -1) 把 [N, Dh] 变成 [Dh, N]，目的是让 q @ k.T 的内维 Dh 对齐。如果随手用 reshape 代替，数字一个不少，但 query 与 key 的坐标关系可能已经被打乱了。

10.4 “bias 也是矩阵乘法的一部分”

bias 是加法项，不是乘法项：

Y=XW⊤+b.

它通常沿 batch 轴 broadcast。把 bias 看作“每个 output neuron 的整体平移”更准确。

10.5 “矩阵乘法越大，信息混合就越好”

不一定。全连接矩阵确实允许任意 input-output 连接、表达能力很强，但参数量和计算量都可能爆炸，而且完全用不上图像的 locality 或图的 permutation structure。卷积用稀疏连接和 weight sharing 换来效率与先验；attention 让内容决定连接；GNN 用 edge structure 路由消息。说到底，矩阵乘法只是底层积木，architecture 才决定哪些积木可以互相连。

12. 性能直觉：为什么 shape 还关系到速度和显存

先抓住本章的核心：Transformer 同时在和两个规模赛跑——N 是 token 数，决定全局 token-pair 交互有多贵；d 是 hidden width，决定每个 token 的 feature mixing 有多贵。Attention 主要支付 N2 的账单，projection 和 FFN 主要支付 d2 的账单；到底谁主导，不是看 “N 大不大” 这么简单，而是看 N/d 的比例。训练时 Transformer 用大规模并行把昂贵的全局交互摊开，推理时 KV cache 避免反复重算历史；但当 N 足够长时，那个平方项仍然会回来敲门。

矩阵乘法的基础账单，先从最简单的这笔算起：

[M,K]@[K,N]⇒约 MKN 个 multiply-add 对.

这里把一次乘法和一次加法合在一起，计作一个 multiply-add 对；如果硬件文档把乘、加分别计作两个 FLOPs，下面的数值系数整体乘 2 即可，大 O 结论不变。shape 之所以能直接决定性能，是因为它决定了矩阵乘法里 M、K、N 到底各自是谁。

总账与临界点：到底是 N² 项还是 d² 项主导？

把 L 层堆叠起来，单个样本一次完整 forward 的粗略账单就是

Ctotal≈L(2N2d+12Nd2)

如果只想看增长阶：

O(LN2d+LNd2).

如果令两项相等，就能找到一条很有用的分界线：

2N2d=12Nd2⟹N≈6d.

于是可以用一个很快的比例判断：

Attention 项projection+FFN 项≈N6d.
N/(6d) 粗略主导项 读法
远小于 1 Nd2 token 还不够长，宽矩阵更贵
接近 1 两者相当 进入真正的折返点
远大于 1 N2d 全局 token-pair 开始碾压线性层

举两个具体数字，免得被“长序列”三个字带跑偏：

  • d=4096 时，粗略临界点是 N≈6×4096=24576，也就是约 25k token。
  • N=4096,d=4096 时，比例约为 1/6；按本节把 FFN 和四个 projection 都算进去的模型，线性项仍约为 Attention 项的 6 倍。Attention 已经是很大的开销，但还不能直接说它占了大头；真实 kernel、batch、硬件和 FFN expansion ratio 会改变常数。
  • N=100000,d=4096 时，比例约为 4.1；此时 Attention 项才明显超过 projection+FFN 项。

这就是 N 与 d 的军备竞赛：增大 d，是让每个 token 变得更“宽”、更有表达容量；增大 N，是让每个 token 面对更多“潜在对话对象”。前者付的是 d2 的账，后者付的是 N2 的账。

为什么 head 数 h 不出现在大 O 里？

每个 head 的宽度是 dh=d/h，把所有 head 的 score 计算加起来：

h×N2dh=N2(hdh)=N2d.

可见在固定 d 的前提下，h 并不改变主阶；它影响的是常数、kernel 利用率、每个 head 的表示粒度，以及 KV cache 的 head 维度。不过要特别留意，显存账单里是会出现 h 的——因为朴素实现可能真的把 [B, h, N, N] 的 score 或 probability tensor 存下来。

12.2 三个互补视角：同一个 N²，三种疼法

同一个 N2，可以从三个角度感受它的重量。把这三个角度分开看，很多“理论上明明一样、实际速度却不同”的疑问就不会互相打架了。

1. 计算视角：FLOPs 是全局视野的门票

Attention 的 QK𝖳 会为每个 query-token 和每个 key-token 生成一个 pair score，数量约为 N2；AV 又要把这张路由表应用到 value 上。不妨把它想成一场大型圆桌会：每个 token 都有机会和全场对话，全局性确实强，但桌上的潜在对话对数也在按平方膨胀。

2. 显存视角：score matrix 可能先把显存吃掉

之所以要警惕显存，是因为朴素实现常会真的物化一个

scores∈ℝB×h×N×N

的 tensor。如果每个元素占 s byte，那么一张 score matrix 就约占

Mscores=BhN2sbytes.

举个例子：B=1,h=1,N=100000、使用 float32（s=4）时，仅一个 head 的一张 [N,N] score matrix 就有

1000002×4=40,000,000,000 bytes≈37.3 GiB.

而这还没算 probability tensor、Q/K/V、output、backward 要保存的 activation 和其他 workspace；如果有 32 个 heads，单张同类矩阵的大小就会来到约 1.28 TB。

FlashAttention 的关键贡献，并不是把数学上的 pair 数量变成线性，而是 IO-aware 的分块计算：它不把完整的 [N,N] score/probability 矩阵写回 high-bandwidth memory，而是在 tile 内就完成 softmax 和 value mixing。于是计算复杂度仍是 O(N2d)，但 attention 中间结果的显存，在固定 d 时对 N 近似线性增长，而不是保存整张 N2 的表。

3. 并行视角：Transformer 贵，但它能一起算

Transformer 的 N2 pair 可以切成许多 block，丢给 GPU 同时计算；RNN 则每一步都必须等上一步的 hidden state，所以虽然单步可能只花 O(d2)，时间轴上的 N 步却很难完全并行。这个 trade-off 可以这样对照：

Architecture 每个位置/时间步的典型计算 序列总计算 时间轴并行性 长程依赖
RNN O(d2) O(Nd2) 受 recurrent state 限制 有一条长链，但可能遗忘
CNN O(kd2) O(Nkd2) 可以并行 单层看局部，需堆层扩大 receptive field
Transformer attention 一个 query 读取 N 个 key：O(Nd) O(N2d) 高度并行 一层就能直接访问全序列

要注意，这张表只比较了 sequence mixing；Transformer 的 projection/FFN、CNN 的 channel 约定和具体 kernel 还会贡献额外的项。另外，别把“总计算量更小”和“端到端延迟更低”混为一谈：RNN 可能 FLOPs 更少，却因为串行而喂不饱硬件；Transformer 可能 FLOPs 更多，却能靠 GPU 的并行吞吐把它摊平。

12.3 自回归生成的账：KV cache 到底省了什么？

先把两个问题分开：一次长度为 N 的完整 forward，标准 attention 本身仍然是 O(N2d)；而自回归生成，是连续做 N 次“从当前前缀预测下一个 token”。KV cache 改变的是后面这个总过程——历史的 K/V 只计算一次、保存起来，之后只做读取。

假设从空上下文开始，每一步生成一个 token，忽略 batch 和 layer 常数。第 t 步如果没有 cache，模型要把长度为 t 的前缀重新跑一遍：

Ctno-cache=O(t2d+td2).

把 t=1…N 的所有步骤加起来：

∑t=1Nt2d=O(N3d),∑t=1Ntd2=O(N2d2),

于是总账就是

Cdecodeno-cache=O(N3d+N2d2).

第 t 步如果有 cache，新 token 只需要做自己的 projection/FFN，并用新 query 读取长度为 t 的历史 K/V：

Ctcache=O(td+d2).

把所有 decode steps 累加起来，得到

Cdecodecache=O(N2d+Nd2).
方案 第 t 步 生成 N 个 token 的总量 省下了什么
无 cache O(t2d+td2) O(N3d+N2d2) 什么都不复用，历史每步重算
有 KV cache O(td+d2) O(N2d+Nd2) 旧 K/V 和旧 token 的 projection/FFN 不再重算

所以准确地说，KV cache 并没有让单个新 query 免于读取全部历史——第 t 步仍然要做约 t 个 key match。它真正改变的，是整个生成过程的渐进复杂度：Attention 部分从反复重算的立方级，降到了平方级。所以说它“只省常数”是不准确的——在长文本生成的总账里，它省掉的是一整个重复计算的维度。

当然，cache 自己也要占显存。若共有 L 层、batch size 为 B、K/V head 数为 hKV、每个 head 宽度为 dh、元素大小为 s byte，那么 K 和 V 的 cache 近似为

MKV≈2BLNhKVdhsbytes.

在 MHA 里 hKV=h；GQA/MQA 减少的正是 hKV，所以能按 hKV/h 的比例缩小 K/V cache 和相关的 memory traffic——但它并不会自动消灭标准 full attention 的 N2 score 计算。

还要区分 prefill 和 decode 两个阶段：把一段已有的 prompt 一次送进模型，是 prefill，这一阶段仍要处理整段 token 的 attention；之后逐 token 生成，才进入复用 cache 的 decode 阶段。

12.4 业界对 N² 的反围剿

先看清一件事：不同路线攻击的是不同的瓶颈，不能把它们笼统地都叫“把 Transformer 变成线性”：

路线 核心思路 Attention 计算趋势 主要省什么
FlashAttention block/tile + IO-aware，不物化完整 score 仍是 O(N2d) 显存读写和中间 tensor，常数显著下降
sliding window 每个 token 只看邻近 w 个 token O(Nwd) 远距离 pair 的计算与显存
sparse attention（如 Longformer） 每个 token 只连接模式允许的 s 个位置 O(Nsd)；若 s≈N，就是 O(N3/2d) 被稀疏模式删掉的 pair
linear attention 用 kernel/代数重排维护固定 state 常见为 O(Nd2) 把 token-pair 表换成 state，通常牺牲 exact softmax 能力
MQA/GQA 多个 Q head 共享较少的 K/V heads 标准 full attention 仍约 O(N2d) K/V cache 和 memory bandwidth
DeltaNet 用 recurrent state + delta update 压缩并改写记忆 教学版总量约 O(Nd2) 不保存完整历史，换取容量/精度取舍

读这张表时抓住一条主线：FlashAttention 主要打显存访问，window/sparse 直接减少连接数，linear attention/DeltaNet 改变历史的表示方式，MQA/GQA 主要压缩推理 cache。它们彼此并不互斥——一个模型完全可以同时用 causal mask、GQA、KV cache 和 FlashAttention。

读一张复杂度表前，先问三个问题

  1. 是在算一次 forward，还是在算整段 autoregressive decode？ 前者的 full attention 是 O(N2d)；后者还要把每个时间步加起来。
  2. 有没有物化 [N,N]？ 计算量不变，不代表显存和 memory traffic 不变；FlashAttention 的价值就在这里。
  3. N 和 d 哪个在增长？ N 长到 6d 附近才会跨过本节粗略账单的临界点；如果 d 也跟着变大，不能只盯着 N2。

最后留一个快速迁移练习：若 d=4096,N=8192，则 N/(6d)=1/3——按本节的完整 layer 模型，projection+FFN 仍然更大。如果把 full attention 改成窗口 w=512，attention mixing 的 pair 数会从约 N2 降到约 Nw，连接数大约减少 N/w=16 倍；但代价是，模型从此失去了直接读取任意远 token 的能力。

15. 为什么 PyTorch 的 W 是 [D_out, D_in]：矩阵的多种视角

在前面的章节里，这个式子已经出现过很多次：

Y=XW𝖳+b,

其中

X:[B,Din],W:[Dout,Din],b:[Dout],Y:[B,Dout].

很多人第一次看到 PyTorch 的 weight，都会冒出同一个疑问：既然输入有 Din 个 feature、输出有 Dout 个 feature，W 为什么不直接写成 [Din,Dout]？先把答案放在最前面：

[D_out, D_in] 不是唯一正确的矩阵排布，而是 PyTorch 选择的参数 convention。它让 W 的每一行对应一个 output neuron，同时也正好符合列向量写法 y=Wx。由于 PyTorch 的 batch 输入通常把每个样本放在一行，所以 forward 写成 XW𝖳。

当然，如果你采用另一种 convention，也完全可以把参数存成 [Din,Dout]，然后写 XW——数学并没有禁止这么做，只是那样一来，你遵循的就不是 PyTorch nn.Linear 的参数契约了。

这一章要回答的不只是“为什么是这个 shape”。顺着这个问题，我们会把矩阵在神经网络里最有用的几种视角依次串起来：以后看到一个矩阵，你可以把它同时看成一张表、一个线性函数、若干 neuron 的权重集合、若干 basis vector 的去向、一个几何变换、一个 batch operator，甚至一张反向传播中的梯度账本。

15.1 先锁定一个最小例子

设每个样本有 3 个输入 feature，线性层产生 2 个输出 feature：

Din=3,Dout=2.

取一组具体数字：

W=[102030405060],b=[100200].

W 的 shape 是 [2,3]。再输入一个 row vector：

x=[123].

PyTorch 的计算是

xW𝖳+b=[123][104020503060]+[100200]=[240520].

逐个 output 写出来更直观：

y0=1⋅10+2⋅20+3⋅30+100=240,
y1=1⋅40+2⋅50+3⋅60+200=520.

可以看到，W 的第一行只负责 y0，第二行只负责 y1。这已经透露出 PyTorch 选择 [Dout,Din] 的第一层原因：输出有几个 neuron，W 就有几行；每一行装着的，是这个 neuron 看待全部输入 feature 的权重。

15.2 从“一个 neuron”推导出 W 的行

与其先背矩阵 shape，不如先问一个更根本的问题：一个 neuron 到底需要什么？

一个 neuron 要接收 Din 个输入 feature，所以它需要 Din 个 weight：

wo=[wo,1wo,2⋯wo,Din].

它产生一个 scalar：

yo=wox+bo.

如果有 Dout 个 output neuron，就把这 Dout 组权重逐行堆起来：

W=[w0w1⋮wDout−1]∈ℝDout×Din.

对列向量 x∈ℝDin×1：

y=Wx+b,y∈ℝDout×1.

矩阵乘法的第 o 行正好是 wox，所以第 o 行对应第 o 个输出。bias 也自然是 [Dout]——每个 output neuron 都配一个自己的偏置。

这么推，比从“矩阵乘法要求内维相等”倒推回去更有解释力：shape 规则只是结果，真正的压力来自网络结构本身——要从 Din 个输入数字产生 Dout 个独立输出数字，你就需要 Dout 个长度为 Din 的加权汇总器。

15.3 两种向量约定：为什么一个人写 W，另一个人写 W.T

其实很多“W 到底该写成 [in,out] 还是 [out,in]”的争论，根源并不是数学冲突，而是大家悄悄把向量的摆放方向混在了一起。把两种 convention 分别摆出来，争论就消失了。

15.3.1 列向量 convention：W 直接作用在 x 左边

数学教材常把一个样本写成列向量：

xcol∈ℝDin×1.

这时最自然的线性映射写法是

ycol=Wxcol+bcol,

所以 W 必须是

[Dout,Din].

因为只有这样，维度才咬得上：

[Dout,Din][Din,1]→[Dout,1].

15.3.2 行向量 convention：PyTorch batch 把样本放在行里

而工程代码里，通常把一个 batch 写成：

Xrow∈ℝB×Din,

每一行是一个样本。为了让输出仍然是一行一个样本：

Yrow=XrowW𝖳+b.

shape 则是

[B,Din][Din,Dout]→[B,Dout].

注意，这里真正参与右乘的是 W𝖳，它的 shape 才是 [Din,Dout]。PyTorch 只是把参数本体 W 存成转置前的 [Dout,Din]，所以代码里才会看到那个 .T。

15.4 矩阵视角一：它是一张带语义的数字表

最朴素的一种视角，是把 W 看成一张表格：

Wo,i

它表示“输入 feature i 对 output feature o 的 weight”。这里的行和列不是空洞的编号，而是两个角色：

位置 语义
行 o 哪一个 output neuron
列 i 读哪一个 input feature
单元格 Wo,i 这个 input 对这个 output 的影响强度

在最小例子中：

W1,2=60

表示第二个 output neuron 读取第三个 input feature 时使用权重 60。索引从 0 开始的代码写法是 W[1, 2]。

这个视角特别适合排查 shape 和语义错误。如果你看到一个 weight 的第一维是 2、第二维是 3，就追问一句：“这是 2 个输出各自读取 3 个输入，还是 3 个输入各自连接 2 个输出？”数字本身回答不了这个问题，参数 convention 才能。

15.5 矩阵视角二：它是很多个 output neuron 的权重集合

把 W 按行拆开：

W=[weights of output 0weights of output 1⋮weights of output Dout−1].

于是每个输出就是对应行与输入的 dot product：

yo=Wo,:x+bo.

这也是最贴近 MLP 的视角。每一行都可以单独拿出来做一个 neuron：

换句话说，矩阵乘法只是把“逐个 neuron 计算”打包成了一次 kernel；GPU 并没有改变这个语义，它只是同时算了很多行、很多样本而已。

15.6 矩阵视角三：它是一个线性映射

但别只把 W 看成一张参数表——更抽象地看，W 是一个函数：

W:ℝDin→ℝDout.

它接收一个 Din 维向量，输出一个 Dout 维向量。如果再加入 bias：

f(x)=Wx+b

严格来说，这时它是一个 affine map（仿射映射），而不是纯 linear map；只有当 b=0 时，它才是线性映射。

在这个视角下，shape 的含义不是“表格有几行几列”，而是：

ℝDin⏟输入空间→WℝDout⏟输出空间.

这立刻解释了为什么第一维是 D_out、第二维是 D_in：矩阵的行数是值域的维度，列数是定义域的维度。一个 2×3 的 W 把三维输入映射到二维输出；要是写成 3×2，默认含义就变成了“把二维输入映射到三维输出”——除非你同时改变乘法方向或转置约定。

15.7 矩阵视角四：W 的列是 input basis 的去向

接下来是最有几何味道、也最容易被忽略的一个视角。设输入空间的标准 basis 是

e1=[10⋮0],e2=[01⋮0],…

W 作用在第 i 个 basis 上：

Wei=W:,i.

也就是说，W 的第 i 列，就是输入 basis ei 被映射到输出空间之后的坐标。

对前面的 W：

W=[102030405060],

逐列写出来，有

We1=[1040],We2=[2050],We3=[3060].

任意输入都可以写成 basis 的线性组合：

x=x1e1+x2e2+x3e3.

代回去，就得到

Wx=x1We1+x2We2+x3We3.

这句话的直觉很妙：输入的每个 coordinate 都拿着自己的系数，去缩放一根“输入 basis 的去向”，最后把所有去向加起来。所以矩阵的列视角回答的是“每个 input feature 会把信息送到哪些 output feature”，而行视角回答的是“每个 output neuron 会从哪些 input feature 收信息”——两者互为对偶。

15.8 矩阵视角五：它是几何变换的坐标规则

对二维输入，W 可以改变平面上的点、线和方向：

W 的结构 几何效果
对角矩阵 各坐标轴独立缩放
正交矩阵 rotation 或 reflection，长度和角度保持
非零非对角项 一个坐标混入另一个坐标，常表现为 shear 或 rotation + scale
rank 小于输入/输出维度 把空间压到更低维的子空间，存在信息丢失
可逆方阵 可把输入空间一一变换到输出空间

看两个例子。

R=[0−110]

它把 (1,0) 变成 (0,1)，把 (0,1) 变成 (−1,0)——这正是逆时针旋转 90 度。

再看另一个矩阵：

Conv2d

15.15 为什么不把 PyTorch 直接设计成 [D_in, D_out]

铺垫了这么多视角，现在可以把“为什么不是反过来”拆成几个真实的原因了：

  1. 每行一个 output neuron 很自然。 weight[o] 就是第 o 个输出的全部输入权重，和 bias[o] 对齐。
  2. 符合 column-vector 的标准线性映射。 y=Wx 直接要求 W 是 [D_out,D_in]。
  3. 和卷积的 output-channel-first 习惯一致。 Conv2d、Conv1d 等也把 output channel 放在 weight 的前面。
  4. 参数初始化和检查更直接。 初始化一个 output unit 的权重，就是取一整行；检查 output width，就是看第一维。
  5. 和 autograd 的梯度 shape 对齐。 batch gradient 是 GY𝖳X，自然得到 [D_out,D_in]。
  6. 历史 API 和底层 kernel 共同形成了 convention。 这不是一个必须由数学唯一决定的答案；换成 [D_in,D_out] 也可以，只是所有接口和 transpose 位置要一起换。

最后一条尤其重要：不要把“PyTorch 这样存”误读成“矩阵只能这样写”。数学、代码和硬件各有各的方向约定，真正不能变的只有数据流契约：

每个 output 都要读取所有 input，输出宽度必须是 Dout.

15.18 转移练习：不看答案先预测

练习 1。 layer = nn.Linear(7, 5) 的 weight 和 bias shape 是什么？输入 x:[4, 10, 7] 的输出 shape 是什么？

答案：weight 是 [5,7]，bias 是 [5]，输出是 [4,10,5]。前两条轴只是 batch-like leading dimensions，Linear 只作用在最后的 7 维上。

练习 2。 W 是 [6,4]，列向量 x 是 [4,1]。W 的一行和一列分别回答什么问题？

答案：一行回答“某个 output neuron 如何读取 4 个 input feature”；一列回答“某个 input basis / input feature，会以多大强度影响 6 个 output coordinates”。

练习 3。 为什么 X:[8,3] @ W:[3,5] 可以运行，但 nn.Linear(3,5).weight 却是 [5,3]？

答案：前者把 W 当作 alternative row-vector parameter convention；后者的参数本体遵循 PyTorch 的 output-first convention，所以要写 X @ layer.weight.T。两者可以表示同一个函数，但 checkpoint 的 shape 不同。

练习 4。 两层 Linear 的 weight 是 W1:[4,3] 和 W2:[2,4]。为什么这个顺序合法？

答案：第一层把 3 维输入映射成 4 维 hidden，第二层读取 4 维 hidden 再映射成 2 维输出；列向量组合是 W2 W1，shape 为 [2,4] @ [4,3] -> [2,3]。

15.19 合上本章：记住一个不容易翻车的模型

看到 PyTorch 的 W:[D_out,D_in] 时，别再只背“输出在前、输入在后”——同时启动下面五个问题：

  1. neuron 视角： 有 D_out 行，每行是一个 output neuron 的 D_in 个权重。
  2. linear-map 视角： W 把输入空间 ℝDin 映射到输出空间 ℝDout。
  3. basis 视角： W 的第 i 列是输入 basis ei 在输出空间的去向。
  4. batch 视角： row-batch 输入用 X @ W.T，同一套 W 复用于所有样本。
  5. gradient 视角： batch 更新是 output-gradient 的转置乘 input，仍然得到 [D_out,D_in]。

最短的 shape 口诀是：

当你能在 row、column、function、geometry、batch、gradient 这些视角之间自由切换时，W 为什么是 [D_out,D_in] 就不再是框架钦定的神秘数字，而是同一条数据流在不同坐标系下的自然结果。

16. PyTorch 显存管理与 Tensor 形状操作

先把下面几句核心判断记住，后面的 API 都只是它们的具体表现：

  1. shape 讲“怎么看”，stride 讲“怎么走”，storage 才是实际存数字的地方。
  2. view 只换解释方式，要求 layout 兼容，并共享原来的 storage。
  3. reshape 先尝试做 view；做不到时会 copy，所以它更方便，但不保证零拷贝。
  4. transpose / permute 交换轴的顺序；squeeze 删除 size 为 1 的轴；unsqueeze 插入 size 为 1 的轴。它们通常只改 metadata，不改变元素总数。
  5. 显存由 numel × dtype bytes 决定只是起点；训练还要加上 gradients、optimizer state、activations 和 temporary workspace。
  6. memory_allocated 是 live tensor 正在使用的显存，memory_reserved 是 PyTorch caching allocator 保留的显存；empty_cache 不能释放仍被引用的 tensor。

这一章的目标很具体：看到一段 PyTorch 代码时，你应该能预测三件事——输出的 shape 是什么、底层 storage 是否被共享、显存为什么会上升或下降。

这一节回答一个经常让人“代码能跑、脑子没跟上”的问题：改变 tensor 的 shape，到底是在改数据，还是只是在换一副看数据的眼镜？

先把四个概念拆开：

  • storage：真正存放数字的一段内存；
  • shape：每条轴有多少个位置；
  • stride：沿某条轴移动一个位置时，底层内存要跳过多少个元素；
  • device：这段 storage 在 CPU memory 还是 GPU memory。

这样，一个 tensor 就可以看成下面这本“账”：

这张图里最重要的箭头是：view、reshape、transpose 先只动 metadata；只有当 layout 不允许继续共享 storage 时，PyTorch 才不得不创建一份 copy。而 device 决定的是这段 storage 住在哪一块显存或内存里。

16.1 一个 tensor 不只有数字：shape、stride、device

对 [3, 4] 的 contiguous tensor，stride=(4,1) 的读法是：沿第 0 轴前进一格，要跳过一整行的 4 个元素；沿第 1 轴前进一格，只需跳过 1 个元素。它可以用下面的地址公式理解：

offset(i0,i1)=storage_offset+i0stride0+i1stride1.

这里 offset 是底层元素位置，storage_offset 是起点偏移，i_0,i_1 是索引，stride_0,stride_1 是两条轴的步长；它们的单位都是“元素”，不是 byte。

16.2 view：只换 shape，共享同一份 storage

view 的核心承诺是：不搬数字，只换解释方式。所以它要求原 tensor 的 stride 能够支撑目标 shape；如果 layout 不兼容，view 会直接报错，而不是偷偷帮你复制一份。

这就是 aliasing（别名）：x 和 y 是两张 shape 不同的“地图”，但指向同一块地。不过要注意，“view 不复制数据”并不等于它永远安全：对参与 autograd 的 tensor 做不恰当的 in-place 修改，可能会毁掉 backward 需要的中间值。

16.3 reshape：优先尝试 view，必要时自动 copy

reshape 的目标更直白：“给我这个 shape”。layout 允许时它就返回 view；无法共享 storage 时，它就创建一个新的 contiguous copy。所以 reshape 用起来更方便，但也少了 view 那个“绝不复制”的强承诺。

所以别把“reshape 一定不复制”或“reshape 一定复制”当成口诀背。如果程序的正确性依赖 aliasing，就用 data_ptr()、_base 和 is_contiguous() 去验证，而不是靠猜。

16.4 transpose / permute：交换轴，通常只改 stride

transpose(dim0, dim1) 交换两条轴，permute(...) 则可以一次性重排所有轴。它们通常返回共享 storage 的 non-contiguous view——底层数字的顺序并没有被重写。

在二维 tensor 上，x.T 就足以表达转置；但在高阶 tensor 上，更建议明确写成 x.transpose(-2, -1) 或 x.permute(...)，因为你需要清楚地指定到底交换哪两条轴。矩阵乘法里那个 attention 例子正是如此：

很多 kernel 或 view 会要求 contiguous layout，这时可以调用 contiguous()：如果 tensor 已经连续，它通常直接返回自身；如果不连续，它就分配新 storage 并复制元素。
